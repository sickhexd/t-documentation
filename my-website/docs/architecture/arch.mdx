# Архитектура системы

## Краткая схема решения

Система строится вокруг веб-приложения для бронирования, оплаты, администрирования и уведомлений. После обработки результата оплаты сервис публикует событие изменения статуса оплаты в RabbitMQ, а сервис уведомлений асинхронно получает это событие и отправляет уведомление пользователю. Ключевые технологические решения и ограничения приведены ниже.

## Нефункциональные требования

### Безопасность

- **NFR-SEC-001 (MUST HAVE):** Передача всех данных через HTTPS с TLS 1.3
- **NFR-SEC-002 (MUST HAVE):** Пароли пользователей хранятся только в виде хеша
- **NFR-SEC-003 (MUST HAVE):** Блокировка после 5 неудачных попыток за 10 минут, сроком на 15 минут

### Производительность
- **NFR-PER-001 (SHOULD / MUST):** Система выдерживает пиковую нагрузку не менее 23 RPS
- **NFR-PER-002:** У 95% пользователей при просмотре свободных мест данные загружаются ≤ 1 сек
- **NFR-PER-003:** У 95% пользователей при создании брони данные загружаются ≤ 500 мс
- **NFR-PER-004:** У 95% пользователей оплата обрабатывается ≤ 800 мс

### Надёжность
- **NFR-REL-001 (MUST HAVE):** Uptime системы не ниже 99% в месяц (Downtime ≤ 7 ч 18 мин)
- **NFR-REL-002 (MUST HAVE):** Резервное копирование БД выполняется ежедневно

### Наблюдаемость (Observability)
- **NFR-OBS-001 (MUST HAVE):** Логирование всех критических операций
- **NFR-OBS-002 (MUST HAVE):** Мониторинг количественных метрик: uptime, RPS, p95
- **NRF-OBS-003 (MUST HAVE):** Все ошибки 4xx, 5xx логируются и генерируют алерт

### Нормативно-правовые требования
- **NFR-REG-001 (MUST HAVE):** Система генерирует и отправляет чек клиенту в течении 5 минут

### Эксплуатационные ограничения
- **NFR-SCAL-001 (COULD):** Увеличение нагрузки до 100 RPS без изменения архитектуры
- **NFR-MAINT-001 (SHOULD):** Ведение API документации в формате OpenAPI 3.0 (Swagger)
- **NFR-COMP-001/002 (SHOULD):** Поддержка основных браузеров и адаптивная вёрстка (320px до 2560px)
- **NFR-CAP-001/003 (MUST/SHOULD):** Хранение данных бронирования не менее 12 месяцев, объём хранилища от 10 ГБ

## Хранение данных

| Пользователи | Тысячи | OLTP | Strong Consistency (ACID) | Uptime 99% | Жёсткая |
| Парковочные места | Десятки–сотни | OLTP | Strong Consistency | Uptime 99% | Жёсткая |
| Тарифные планы | 1–10 записей | OLTP | Strong Consistency | Uptime 99% | Жёсткая |
| Платежи | Тысячи–десятки тысяч | OLTP | Strong Consistency | Uptime 99% | Жёсткая |
| Брони | Тысячи–десятки тысяч | OLTP | Strong Consistency | Uptime 99% | Жёсткая |

| Логи запросов | Миллионы | Event Streaming | Eventual Consistency | Средняя | Гибкая |
